# Install Promptus in production

Promptus runs as one Docker Compose stack: the **app** container (the
Axum server, which also serves the built front) and **PostgreSQL 17**.
A front door in front of it terminates TLS. On Romain's server players
and GMs reach it over **NetBird**, never from the open Internet.
Backups and restores: [backup.md](backup.md).

```
phone (NetBird) ──https──> Caddy on PCT 105's NetBird address ──http──> app 127.0.0.1:4380 ──> postgres
                           (/opt/promptus-door)                         (this stack, /opt/promptus)
```

What is where:

| File | Role |
| --- | --- |
| `Dockerfile` | Multi-stage: Bun builds the front, Rust builds the server, a `debian:trixie-slim` runtime holds both (~170 MB) |
| `docker-compose.prod.yml` | The production stack (`app` + `postgres`) |
| `.env.production.example` | Every setting; copied to `.env.production` (gitignored) |
| `deploy/install.sh` | First install: writes `.env.production` with fresh secrets, builds, starts |
| `deploy/backup.sh` / `deploy/restore.sh` | [backup.md](backup.md) |
| `deploy/prod-deploy.sh` | Continuous deployment from the Proxmox host (below) |

## What the app does at start

1. Reads its settings from the environment (`docker-compose.prod.yml`
   builds them from `.env.production`).
2. Connects to PostgreSQL and **applies pending migrations** before
   answering anything. A migration that fails stops the start: the
   container restarts in a loop and its log says why
   (`docker compose … logs app`).
3. Serves `/api/*` and, for every other path, the built front
   (`FRONT_DIR=/srv/front` in the image). Client-side routes such as an
   invite link get `index.html`; hashed files under `/assets/` are
   cached for a year; the shell itself is never cached, so a deploy
   reaches browsers at their next load.

**Health check:** `GET /api/health` answers `200 {"data":{"status":"ok"}}`
only when the server is up **and** its database answers; `503` otherwise.
The image's `HEALTHCHECK` and `docker compose up --wait` both use it.

## Requirements

- A Linux machine (or LXC container) with Docker and the compose plugin.
  On Proxmox, an unprivileged LXC needs `nesting=1,keyctl=1` to run
  Docker.
- ~2 GB of free RAM and a few minutes of CPU for the first build (the
  Rust release build), ~5 GB of disk for images and build cache.
- `openssl` (install script), `git` (deploys, backup manifest),
  optionally `age` (encrypted backups).

## First install

On the machine that runs the stack, from a checkout of the repository:

```bash
deploy/install.sh
```

It asks for the public name (e.g. `promptus.secretofarasgrasa.com`),
writes `.env.production` (mode 600) with a generated database password,
builds the image and starts the stack, waiting for the health check.
An existing `.env.production` is never overwritten; re-running the
script only rebuilds and restarts.

Then check, on that machine:

```bash
curl -fsS http://127.0.0.1:4380/api/health
```

### Settings (`.env.production`)

| Variable | Default | Meaning |
| --- | --- | --- |
| `PROMPTUS_DOMAIN` | — (required) | Public name, without `https://`. Allowed as a CORS origin |
| `POSTGRES_PASSWORD` | — (required) | Generated by `install.sh` |
| `PROMPTUS_BIND` | `127.0.0.1` | Address the app port is published on. Set the machine's LAN address when the reverse proxy runs on another machine |
| `PROMPTUS_PORT` | `4380` | Port published on `PROMPTUS_BIND` |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM` | unset (codes in the log), `587` | The relay that sends GM sign-in codes. 587 is STARTTLS, 465 TLS from the start. `SMTP_FROM` is required with `SMTP_HOST` |
| `PROMPTUS_APP_ORIGINS` | `tauri://localhost,http://tauri.localhost` | Origins of the desktop and phone shells allowed to call the API |
| `OPENROUTER_API_KEY` | unset (AI off) | The OpenRouter key every AI call uses (co-GM, generation, images, videos). Each campaign's AI budget caps what it may spend |
| `OPENROUTER_MODEL`, `OPENROUTER_IMAGE_MODEL`, `OPENROUTER_VIDEO_MODEL` | `anthropic/claude-sonnet-4.5`, `google/gemini-2.5-flash-image`, `google/veo-3.1` | The models, by OpenRouter id |
| `AI_PRICE_INPUT_PER_MTOK`, `AI_PRICE_OUTPUT_PER_MTOK`, `AI_PRICE_PER_IMAGE`, `AI_PRICE_PER_VIDEO` | `3`, `15`, `0.04`, `4` (dollars) | What a call is estimated at before it leaves: the budget refuses on the estimate, the real cost is recorded after. Match them to the models chosen |
| `PROMPTUS_BACKUP_DIR`, `PROMPTUS_BACKUP_KEEP`, `PROMPTUS_BACKUP_AGE_RECIPIENT` | | [backup.md](backup.md) |
| `COMPOSE_PROJECT_NAME` | `promptus` | Only to run a second, test stack next to the real one |
| `RUST_LOG` | `info` | Server log level |

The database port is never published: only the app reaches it, on the
stack's private network.

### GM accounts

A GM signs in at `https://<PROMPTUS_DOMAIN>/connexion` with their email:
the app sends a six-digit code, valid ten minutes, and the first time
asks for the name players will see. **Anyone who reaches the app can
become a GM**; each GM only ever sees their own campaigns. Players have
no account at all: they join from a GM's invitation link.

Open sign-up is acceptable because the app is not on the Internet:
on Romain's server it is only reachable over NetBird (below). Exposing
it publicly would need an allow-list of GM addresses first.

Without SMTP the codes are written to the app's log:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.production logs app | grep "sign-in code"
```

### Driving the stack by hand

The scripts pass the production file and env file for you. By hand:

```bash
alias pcompose='docker compose -f docker-compose.prod.yml --env-file .env.production'
pcompose ps
pcompose logs -f app
pcompose up -d --build --wait     # rebuild and restart after a git pull
```

## Reaching it

On a generic server, any reverse proxy that terminates TLS and forwards
to `PROMPTUS_BIND:PROMPTUS_PORT` works; WebSocket upgrades must be
forwarded (the live session channel lives under `/api`).

### On Romain's server: behind NetBird (since 2026-10-10)

The stack runs in **PCT 105** (`/opt/promptus`), next to the development
database, bound to `127.0.0.1:4380`. Players and GMs reach it at
`https://promptus.secretofarasgrasa.com` over NetBird only — the same
model as Devotion in PCT 104:

| Piece | Where | What it does |
| --- | --- | --- |
| NetBird agent | PCT 105, native (`/dev/net/tun` added to `/etc/pve/lxc/105.conf`) | Peer `promptus`, setup key, group `srv-promptus`, no login expiry. Docker waits for it (`docker.service.d/after-netbird.conf`) |
| NetBird policy | `promptus-acces` | `admin` and `team-promptus` → `srv-promptus`, TCP 443 only |
| NetBird DNS zone | `promptus.secretofarasgrasa.com` | A record to the peer's NetBird address, distributed to `admin` and `team-promptus` |
| Front door | PCT 105, `/opt/promptus-door` (Caddy, host network) | HTTPS on the NetBird address and on the LAN address `192.168.1.192` (for the Proxmox host's Claude MCP, via `/etc/hosts` there), proxies to `127.0.0.1:4380`. Separate compose project, untouched by deploys |
| Certificate | PCT 100, `/etc/traefik/conf.d/promptus.yml` | A router that only obtains the Let's Encrypt certificate (TLS challenge) and refuses every request: from the Internet the name answers 403 |
| Certificate copy | Proxmox host, `/usr/local/bin/promptus-cert-sync`, cron 04:37 | Copies it from Traefik's `acme.json` to `/etc/promptus/tls/` in PCT 105 and reloads Caddy |

The public DNS record (Ionos) points at the home's public address; it
only exists for the certificate challenge.

**Giving someone access** — a player or another GM: add `team-promptus`
to their NetBird user's `auto_groups`. No policy to touch.

⚠️ **Never trust the client IP for security.** The Freebox presents
part of the inbound traffic to PCT 100 with its own address
`192.168.1.254` and adds no `X-Forwarded-For` (`/mnt/storage/CLAUDE.md`,
"Why Bibliotek does NOT go through PCT 100"). Promptus authenticates
people, not addresses.

## Continuous deployment

`deploy/prod-deploy.sh` is Devotion's deploy loop for Promptus. It runs
on the **Proxmox host** from cron every 5 minutes: it fetches `main`
from GitHub (the host holds the key; the container does not), and when a
new commit appears it pushes it into the container as a git bundle,
then, inside the container:

1. `deploy/backup.sh` — **no backup, no deploy**;
2. checks out the new commit;
3. `docker compose … up -d --build --wait` — rebuilds, restarts, waits
   for the health check (migrations run at start);
4. prunes dangling images and build cache older than 72 h.

A commit that fails is not retried (each try would take a backup and
rotate good ones out); the next commit on `main` is. To retry the same
commit: `rm /var/lib/promptus-deploy/failed`.

Install it once the container is chosen and holds a checkout with its
`.env.production`:

```bash
# On the Proxmox host
install -m 0755 deploy/prod-deploy.sh /usr/local/sbin/promptus-deploy
echo 'PROMPTUS_CTID=105' > /etc/default/promptus-deploy   # PROMPTUS_PROD_DIR if not /opt/promptus
/usr/local/sbin/promptus-deploy                                # first run by hand
# crontab -e:
*/5 * * * * /usr/local/sbin/promptus-deploy >> /var/log/promptus-deploy.log 2>&1
```

The container's checkout needs `git` and a first clone, made from the
host the same way (`git bundle` + `pct push`, then `git clone
/root/promptus.bundle /opt/promptus`).

Like Devotion, it follows `main` without waiting for CI.

## Roll back

First stop the deploy loop from bringing the bad commit back within
five minutes — on the Proxmox host:

```bash
echo <bad commit sha> > /var/lib/promptus-deploy/failed
```

It then skips that commit and deploys the next one pushed to `main`.
Then, in the container:

```bash
cd /opt/promptus
git log --oneline -5                       # find the previous good commit
git checkout --detach <commit>
pcompose up -d --build --wait
```

If the bad commit applied a migration the older code does not know, the
older server refuses to start (sqlx reports a migration applied but
missing). Then restore the backup taken just before that deploy — the
newest archive older than the deploy, see [backup.md](backup.md):

```bash
deploy/restore.sh backups/promptus-<date>-<time>.tar --force
```

Anything written between that backup and the restore is lost; the
restore itself first saves the database it replaces.
